# Inspection, security and cleaning

Business implementation is `server/inspections/{model,calendar,resources,service}.ts`, API `server/routes/inspections.ts`, provider `server/providers/inspections.ts`, UI `client/pages/inspections/`, copy `client/locales/inspection-*.ts`. Migration `202610180006_inspections` owns plans/tasks/issues/events/operations. Public API is described in Swagger. User workflow and retained demo numbers are in [the guide](../../docs/巡检安保保洁与异常整改.md).

- Use LifecycleRuntime with the transaction connection. Record business version and lifecycleVersion are distinct; expectedVersion guards business CAS. Every action uses persistent requestId+actor+intent hash; replay returns the original result and cannot create another task/issue/repair.
- Scope every plan by ALL its assets; tasks/issues by their snapshot asset. Composite inspection scope intersects existing asset read. Minimal asset/assignee picker endpoints require manage; do not expose whole user directory to executors. Actual execution and rectification additionally require current assignee. Source and linked repair reads retain their own scopes.
- Frozen task payload captures items/asset/plan version/assignee. Plan editing must not rewrite generated tasks. Unique nullable generationKey(plan,date,asset) and activeItemKey(task,item) enforce deduplication. Abnormal results require an issue and cannot be erased by normal/partial saves. Partial Save allowed; Submit requires all results; task completion/cancellation blocked by any open issue.
- Issue close requires explicit review. Linked repair must be closed before rectification or approval; cancelled is not fixed. Replacements preserve repairHistory. `RepairService.createPrepared` creates within the SAME passed inspection transaction, after existing report+read permissions. Its optional origin metadata is internal; never add origin IDs to public repair input schemas.
- Sorted project locks coordinate inspection/asset/repair writes. Recheck scope and project identity inside the transaction, including linked repair stage. Do not nest the database manager transaction when calling repair creation.
- Scheduler code schedule inspections.dispatch targets app.inspections.dispatch every5minutes Asia/Shanghai. Per-process round-robin attempts at most5plans/100task references, each plan cursor advances at most31dates. Durable cursors recover restarts; uniqueness prevents manual/automatic duplicates. Do not skip failed plans by advancing their cursors. Use creator CURRENT authorization and enabled person, not unrestricted system access. Failed plans cause failed visible occurrence. Existing singleprocess scheduler adapter is unchanged; distributed execution is unverified.
- Route params inspectionPlanId/inspectionTaskId/inspectionIssueId are distinct to avoid nested useParams shadowing ancestors. Read-only sources use inspectionLeafId; no recursive related repair leaf. Linked repair detail disables its reverse inspection block while inside an issue; Back returns to the issue. Preserve originating queries and local list scopes.
- Events store action data under payload.details and actorName/assigneeName beside it. Never read note directly from payload. History paged20, related previews10 and View all. Blocked links render native disabled buttons to avoid BaseUI nativeButton warnings.
- Tests in tests/inspections cover recurrence, real migration, API lifecycle/security/concurrency/scheduling, and UI. Scope checks to these plus impacted repairs/assets/route tests; smallest supported client/server TS projects. Retained live demo records are requested business history, not required seeds.
