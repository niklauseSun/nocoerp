# 多级审批与业务生效

审批按项目和业务类型配置，入口 `/approvals`，页面授权 `hyl-approvals`。业务范围明确为新签合同生效、草稿账单发布、采购申请审批；续租和退租仍沿用既有独立租赁操作。

- `server/approvals/` owns source adapters, authorization, gate checks, configuration and request services. `server/routes/approvals.ts` owns authentication, validators and OpenAPI DTOs. `server/providers/approvals.ts` registers the service and `hyl.approvals` resource. The shared Hyl lifecycle runtime registers approval requests and draft/active contracts; do not create a second runtime to bypass its transaction.
- Configurations use the installed `StoredLifecycleParameters` contract and six application-owned parameter collections. Scope is authoritative `projectId:kind`. First successful submit freezes parameters; rejected resubmission retains this snapshot. Explicit user alternatives use positive distinct reviewer groups. Each named level resolves active, authorized people excluding the applicant; zero candidates fails. A round persists fixed candidates and a fresh source version/business snapshot. Source permission and active identity are checked again at decision.
- Requests have `draft/pending/rejected/approved/cancelled` lifecycle state, ordered level, round, version and append-only opinions. Source business availability stays on the source, not in a second workflow status column. Pending sources are immutable through original endpoints. Domain services invoke `gate.ts`; deleting an approval panel never removes enforcement.
- Final approval and contract asset binding + lease activation, bill issue + receivable posting, or native purchase approval share one database transaction. Internal callbacks in BillingService/ProcurementService join their existing merchant/project serialization; never authorize through the root connection while a SQLite transaction is held. Resolve policies before opening it and recheck the actual source/assets through the callback connection. Parameter store transaction arguments must be transaction handles, never the ordinary main connection.
- `hyl.approvals` actions read/configure/submit/decide/cancel each grant an asset scope. Both the authoritative project and original business permissions must pass. Count/list filter authorized sources before pagination. Decision actors need the corresponding final domain action; grant page access separately. Do not seed broad existing-role grants. Users/roles are administered through public installed plugin services.
- Operation IDs are actor + normalized-intent fenced, version/CAS guarded and source-serialized. Same-key retries recover committed outcomes. Different keys at the same level/version have one winner. Failed effects roll back opinion and operation records. Reject unlocks editing; native purchase return goes to draft. Cancellation preserves history and permits a new request using current configuration.
- New contract drafts have no asset occupancy and cannot enter deposit, billing or settlement operations. Financial entry points must use the correct business action when calling HylService.get; `read` is not a financial authorization. Existing effective contracts retain state. Approval contracts with assets must belong to one project; unbound/no-asset contracts have no project configuration.
- Client source panels use local covering child routes `approvalSubmit` and `approvalRequests/:approvalRequestId`, preserving the invoking detail and search. Center detail uses `/approvals/requests/:approvalRequestId`. Distinct query names `approvalKind/approvalSourceId` prevent collisions. Reject/cancel and every approve have named confirmation and required opinion. Unknown results freeze request body/key for recovery; 409 keeps draft for deliberate revision refresh. Hide cached details/actions after 403/404.

Tests live in `tests/approvals/` (real database migration up/down, domain integration/concurrency/security, component behavior), with affected route and business tests. The explicitly authorized local demonstration command is `pnpm nocobase app approvals-demo --dry-run --json`, then `pnpm nocobase app approvals-demo --json`. It creates only three named local demo identities, scoped project/demo merchant grants and labeled business records. Passwords are randomly generated and never printed; it refuses production. It is not a seed and never runs at installation. Preserve unrelated permission configuration.
