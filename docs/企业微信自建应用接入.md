# 企业微信自建应用接入

入口为“系统管理 → 企业微信”。本期针对单企业自建应用，提供明确的用户/部门映射、双向资料同步、冲突比较、执行记录，以及现有个人业务提醒的企微应用消息投递。

## 接入配置

部署管理员在 **服务器的 `config.yml`** 中填写下列配置，或使用对应的 `WECOM_*` 环境变量。不要将真实 Secret 写入版本库或聊天记录。修改后重启应用。

```yaml
wecom:
  enabled: true
  corpId: '企业 ID'
  agentId: '自建应用 AgentID'
  appSecret: '自建应用 Secret'
  contactsSecret: '具备通讯录写入权限的 Secret'
  readSecret: '' # 可选；未填时使用 appSecret 读取
  autoSync: false
  notifications: false
app:
  publicOrigin: 'https://实际访问域名'
```

环境变量为 `WECOM_ENABLED`、`WECOM_CORP_ID`、`WECOM_AGENT_ID`、`WECOM_APP_SECRET`、`WECOM_CONTACTS_SECRET`、`WECOM_READ_SECRET`、`WECOM_AUTO_SYNC`、`WECOM_NOTIFICATIONS`。公开访问地址可用 `APP_PUBLIC_ORIGIN`。

企微侧需要允许服务器出口 IP，给读取应用足够的通讯录可见范围、给写入凭证通讯录编辑权限。读取凭证与写入凭证分开使用：有些通讯录同步凭证不能读取完整姓名、邮箱等信息，应使用有权限的自建应用凭证读取。应覆盖同步人员的**完整部门归属及其所有上级部门**，不要以局部可见范围进行完整归属同步；读取缺失或接口拒绝时本系统停止该条同步。具体可用字段以该企业实际接口授权为准。如果企微返回格式有效但经过可见范围裁剪的部门列表，系统无法仅凭该响应判断是否完整；启用自动同步前必须由企业管理员核实全量可见范围，缩小范围后应先关闭自动同步。

“检查连接”只进行读取和获取令牌，验证部门读取、写入令牌获取及应用读取。它不创建人员或发送消息，也不能证明通讯录写接口已授权；首次写入的实际返回是写权限验证。

页面只返回企业/应用 ID 和各能力是否配置，不返回凭证。换企业 ID 后旧映射不复用；已冻结的消息在企业或应用 ID 不匹配时拒绝发送。

## 首次同步

1. 先建立根部门映射：企微部门 ID `1` 对应系统的顶层部门；可选已有本地部门，或仅填 `1` 从企微创建本地部门。
2. 打开映射对比页，核对资料后选择“同步到系统”。企微根部门不允许从系统修改。
3. 按上级在先的顺序建立子部门映射，再建立人员映射。
4. 只有企微 ID：首次“同步到系统”创建本地记录。只有本地记录：系统预分配企微 ID，首次“同步到企微”创建企微记录。两边都有：明确指定关联，首次同步选择采用的一边。
5. 人员使用企微 **UserID**，不是姓名。部门使用数字 ID。系统不自动按姓名或邮箱合并已有身份；邮箱冲突会拒绝创建，管理员应核实后使用已存在的本地账号建立映射。

同步字段：部门名称、上级；人员姓名、邮箱、全部部门归属、主部门和启用状态。当前用户体系没有手机号字段，因此本期不同步手机号。企微人员须返回有效邮箱，才能创建或同步系统登录身份。新增本地用户使用随机且不展示的初始密码，不自动授予任何角色；由系统管理员通过现有用户管理重置密码或配置登录方式。这一接入不包含企微扫码免登。

系统部门停用不能直接等价为企微删除，故拒绝推送停用部门。删除、离职记录消失、无权读取不会触发另一边的数据删除。业务角色、项目数据范围和业务历史记录不随通讯录复制。身份映射一经建立不可随意换绑；需要调整时应先核实身份和消息投递历史。

## 日常同步和冲突

手动同步每次读取两边最新资料并校验对比指纹。打开页面后数据变化时，提交被拒绝，需重新刷新比较。双方数据与上次成功同步基线比较：只有一边改变，建议采用该边；两边都改且不一致，列为冲突，不按时间戳强行覆盖。成员部门必须先映射；缺少依赖会停止该条操作。

将 `autoSync` 设为 `true` 后，每五分钟检查最久检查的至多 20 条已完成首次同步的映射。未映射的新人员和部门不自动发现或自动创建，需要先新增映射。多于 20 条可能超过五分钟一轮。自动任务使用部署管理员显式启用的集成权限，不继承某个已退出登录的管理员会话；高权限账号仍受系统保护角色的停用约束。多实例部署沿用项目的持久化 jobs 配置要求。

系统与企微无法组成跨系统数据库事务；企微写接口也没有本地版本条件更新。提交前重新比较可检测已发生的修改，但无法完全消除读取之后、外部接口提交之前其他人在企微修改的窗口。建议同步期间避免同时编辑同一对象。

超时或进程退出可能导致结果未知。系统保留冻结的操作目标并阻止再次写入：

- “核实执行结果”只读取双方资料；与原目标完全一致才确认外部写成功。
- 执行中至少等待两分钟再核实。若本地拉取事务未提交，可解除为失败并重新比较；本地写入和映射提交属于同一事务。
- 外部结果不明且资料不一致时保持阻止状态；管理员需核实企微后台和系统资料，恢复到原目标后再核实。不能用点击重试盲目重复创建。

对比页显示最近 20 条执行记录，完整历史保留在 `hylWecomAudit`。日志只保留操作对象、操作者、方向、结果与安全错误码，不记录令牌、密码或完整远端错误。

## 消息通知

设 `notifications: true`，完成用户映射及首次同步，再由用户在现有消息偏好中启用业务提醒。合同、账单、报修、采购待办沿用已有个人订阅和实时业务权限检查，额外发到该用户的企微自建应用；不向全员或群机器人广播。消息只含通用提醒和需登录的待办链接。站内收件箱独立投递，不因企微失败而丢失。

消息接入复用官方 Notification 的持久化队列、投递状态和重试生命周期；发送前冻结企业/应用/收件人/文案，同一待办代次使用稳定幂等键。企微端可能已接收但响应丢失时记为结果未知，不自动重发。待办详情展示企微投递状态；明确失败可以通过原“重试”入口重试原投递，不能替换身份或伪造已读。当前不回传企微已读状态。

消息链接必须配置外部可访问的 `app.publicOrigin`，且带应用实际部署前缀。尚无真实凭证时仅能完成隔离数据库、模拟企微响应和组件验证；正式启用需要使用实际应用可见范围内的测试员工联调。

## 权限与验证

页面需 `settings:hyl.wecom/read`。读取接口还需组织读取和用户读取权限；写入接口需 `settings:hyl.wecom/update`、组织更新以及用户 read/create/update/disable/enable。普通员工不自动获得这些权限。保护账号不允许通过同步绕过停用约束。

测试位于 `tests/wecom/`，覆盖基线比较、令牌缓存、超时分类、匿名和越权、迁移 up/down、双向同步、部门依赖、冲突和恢复、消息身份冻结及页面交互。真实企微租户权限和 PostgreSQL 并发需在部署环境进一步验证。

参考：企业微信团队发布的 [API 示例库](https://github.com/sbzhu/weworkapi_python)、[创建成员](https://developer.work.weixin.qq.com/document/path/90195)、[部门管理](https://developer.work.weixin.qq.com/document/path/90205)、[发送应用消息](https://developer.work.weixin.qq.com/document/path/90236)。官方文档页面在开发环境中无法直接抓取，调用路径以团队示例库核对，实际字段可用性仍须真实租户联调。
