# 组织权限与项目数据隔离

入口为“组织权限”，包含组织架构、项目数据权限、用户角色、用户目录。组织维护、角色配置和用户管理分别授权；仅能维护部门的人不能因此编辑角色或分配系统管理员。

## 配置顺序

1. 创建部门及上下级，添加有效用户，可将一个部门设为主部门。一个用户可有多个有效部门，但最多一个主部门。
2. 在项目数据权限中，将项目授给用户或部门。部门项目范围传给有效下级成员。
3. 新建岗位角色，在官方权限编辑器中勾选页面与业务动作。每个动作的相关数据范围选择“本人获授权项目”；财务报表同时配置合同与资产两项范围。
4. 在角色详情中授给用户或部门。角色直接授权与部门继承相互独立，撤销其中一个来源不会删除另一个来源。
5. 用户目录展示直接角色。部门继承会在每次请求时重新计算；用户目录链接可进入角色详情管理授权。

只有系统授权管理员可配置角色和授权。组织页面检查 `settings:hyl.organization` 的 `read` / `update`；角色工作区检查 `settings:authorization.permission-sets` 的 `read/create/update/assign`。平台的撤销角色授权也由 `assign` 控制。用户目录检查 `user:*/read`。页面权限本身不授权业务 API。

## 数据范围

`hyl.assignedProjects` 是权限集的数据范围选项，**不是强制覆盖其他角色的租户隔离规则**。用户的多个正向授权取并集；另一个角色的“全部记录”会扩大访问范围，配置界面有明确提示。上线使用前应检查账号的全部直接与继承角色。

资产按 `projectId` 选取。商户范围由资产绑定及合同的资产清单计算；跨项目共用商户只有在其全部关联项目均获授权时可见。没有可证明项目关系、关联资产已缺失、合同未绑定资产的记录不会凭空获得项目访问权限。合同、报送、费用和结算沿相同商户边界关联；计费、押金、收银、开票、分账、能耗、报修、巡检、采购、审批及财务报表继续执行各自的原始父单据权限。

此保守规则可能让跨项目共用商户的部分单据暂不可见；应授予其完整项目范围，或由业务明确设计更细的商户信息边界。使用此范围的普通用户不能创建尚未归属项目的商户；管理员先建立商户与资产绑定后，再由项目人员维护关联业务。新项目由具备全局资产权限的管理员建立，然后授予项目范围。

停用上级部门后，该部门和整个下级链的继承均无效。移动部门会重新计算祖先来源，循环父子关系被拒绝。停用、移除成员、项目授权变化在事务提交后通知受影响账号刷新客户端权限；回滚不会发布成功通知。服务端新请求始终重新解析。业务查询缓存加入账号身份及权限版本，跨账号或撤权后不复用旧列表、资产详情及财务汇总。操作审计只保存组织业务变更，不保存密码或会话凭据。

权限集定义与分配存储由 Authorization 插件拥有，用户与会话由 Users/Authentication 拥有，本模块不另建角色权限表。保护的根角色不可通过普通编辑器修改，最后一个有效管理员受平台保护。已有角色、用户和项目授权不被初始化重置。

## 验证范围

独立测试数据库通过真实登录与 HTTP 校验 401/403、部门维护与角色配置分离、页面单独授权、资产/合同/账单/收银订单/结算/采购订单/水电表/报修工单/巡检计划的外项目详情、原单据子资源与汇总隔离、撤权及禁用会话、最后管理员保护、循环树与版本冲突、唯一主部门、独立授权来源和迁移 up/down。

读取能耗、报修、巡检、审批、开票、分账列表时校验项目过滤；其来源级细节另由相关模块既有集成测试验证。浏览器使用当前管理员会话查看组织、角色和项目授权，并跑新增/改名/搜索；普通账号的实际登录与拒绝路径由 HTTP 集成测试完成，未通过浏览器切换这三个随机凭据账号。原生窄屏、其他外观预设及操作系统 IME 未在本次浏览器环境验证；组件测试覆盖输入法组合事件和权限缓存切换。
